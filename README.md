# AI Security Sandbox — Project Guide

## 1. What Are We Building?

We are building an AI Security Sandbox that allows AI models to be tested in a controlled and repeatable environment.

The basic system will provide predefined test prompts or test cases to an AI model, collect its responses, evaluate those responses according to specific criteria, and store the results. The same tests can then be performed on different models so that their behaviour and security performance can be compared.

The first version will be intentionally simple. Our goal is to understand how the complete system works and create a functional foundation before adding more advanced features.

The basic flow is:

**Select Model → Run Test → Receive Response → Evaluate → Store Result → Compare Results**

---

## 2. Initial Project Goal

The first version of the project should be able to:

1. Connect to an AI model or API.
2. Send predefined test cases to the model.
3. Receive and record the model's responses.
4. Evaluate the responses using basic predefined criteria.
5. Store the test results.
6. Display or compare the results.

At this stage, we are not trying to build a perfect automated security evaluator. We are building the basic framework that can later be expanded.

---

## 3. How We Will Develop the Project

The project will be developed in stages.

### Stage 1 — Basic Working System

Create a simple application that can send a test input to an AI model and receive a response.

### Stage 2 — Testing System

Create a collection of predefined test cases and a system that can run them consistently.

### Stage 3 — Evaluation

Create basic criteria for determining how a model responded to each test.

### Stage 4 — Results

Store the responses and evaluation results so they can be viewed and compared.

### Stage 5 — Expansion

After the basic system works, we can add more models, more advanced tests, automated evaluation, improved interfaces, and other security-testing capabilities.

---

## 4. Team Responsibilities

The project will initially be divided between four main areas.

### Person 1 — UI

Responsible for creating the user interface.

The UI should eventually allow a user to select a model, start tests, and view the results.

The UI should communicate with the main system instead of directly controlling every part of the project.

---

### Person 2 — Main System / Integration

Responsible for the main application logic that connects the different parts of the project.

This part will eventually connect the UI, model/API communication, testing system, evaluation system, and result storage.

The integration code should keep the different modules organized rather than putting the entire project into one large file.

---

### Person 3 — Testing Module

Responsible for creating and managing the test cases used to evaluate AI models.

The testing module should be designed so that new tests can be added later without rewriting the entire application.

The initial version should focus on creating a simple and consistent testing structure.

---

### Person 4 — Results and Data

Responsible for handling the results generated by the tests.

This includes organizing responses, evaluation scores, and other relevant information so that the results can later be stored, displayed, filtered, and compared.

---

## 5. Important Development Rule

Do not directly make changes to the `main` branch unless specifically required.

The `main` branch represents the stable version of the project.

Each developer should normally create a separate branch for their work.

Example:

```text
main
│
├── ui
├── testing
├── results
└── integration
```

A developer works on their branch, commits their changes, pushes the branch to GitHub, and creates a Pull Request.

The changes are reviewed before being merged into `main`.

---

The standard workflow for team members is:

```text

       ↓

       ↓

       ↓
Test Your Changes
       ↓
Commit Changes
       ↓
Push Branch to GitHub
       ↓
Create Pull Request
       ↓

       ↓
Fix Issues if Required

```

Everyone should understand this workflow before making major changes to the project.

---

## 7. Commits

A commit is a saved point in the project's development history.

Commits should describe what was changed.

Good examples:

```text
Add initial testing structure
Create model connection module
Add result storage
Fix response handling
Create basic results page
```

Avoid unclear commit messages such as:

```text
changes
update
final
new
stuff
```

---

## 8. Pull Requests

A Pull Request is used when a developer wants their changes to become part of the main project.

Before creating a Pull Request, the developer should:

* Test their code.
* Make sure their changes are related to their assigned task.
* Check that they have not unnecessarily changed someone else's work.
* Explain what they changed.
* Mention anything that still needs attention.

The project reviewer will check the Pull Request and either approve it, request changes, or discuss the implementation with the developer.

---

## 9. Working With Other People's Changes

Because multiple people will be working on the same project, conflicts may happen.

Before starting new work, developers should make sure their local project is updated with the latest approved changes.

If a conflict occurs, do not randomly delete or overwrite another person's code. Discuss the conflict and resolve it carefully.

The purpose of GitHub collaboration is not simply to upload code. It is to maintain a shared project while allowing multiple people to work independently.

## 11. API Keys and Sensitive Information

API keys, passwords, tokens, and other private credentials must never be written directly into the source code or uploaded to GitHub.

Use environment variables or another appropriate method for handling private credentials.

For example, code should not contain:

```python
API_KEY = "my-secret-key"
```

The actual key should remain outside the repository.

If a configuration file containing sensitive information is used locally, make sure it is excluded from Git using `.gitignore`.

---

## 12. How We Should Work as a Team

Everyone should first understand the purpose of their assigned module before writing large amounts of code.

When implementing something new:

1. Understand what the module is supposed to do.
2. Discuss the expected input and output if it interacts with another module.
3. Build the smallest working version.
4. Test it.
5. Commit it.
6. Push it to your branch.
7. Create a Pull Request.
8. Respond to review feedback.
9. Merge only after approval.

The goal is to build the project gradually and understand why each part exists.

---

## 13. First Task

The first task for the team is not to build the complete AI Security Sandbox.

We will first create a very small working foundation.

The initial program should demonstrate the basic concept:

```text
Program starts
      ↓
Test input is created
      ↓
Input is sent to a model
      ↓
Model response is received
      ↓
Response is displayed
```

Once this basic process works, we can begin separating it into proper modules and adding the testing, evaluation, storage, and UI components.

---

## 14. Long-Term Direction

The long-term goal is to develop the project into a more capable AI security testing platform.

Possible future areas include:

* Larger collections of test cases.
* Automated evaluation.
* Multiple AI model providers.
* Model-to-model comparison.
* Result visualization.
* More detailed security metrics.
* Repeated and automated testing.
* Better isolation and sandboxing.
* More advanced analysis of model behaviour.

These are future possibilities, not requirements for the first version.

The team should focus on creating a small, working foundation first and expand from there.
